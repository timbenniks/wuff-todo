# Feature title

## Problem and intended users

## Agreed scope

Included behavior, deferred ideas and existing behavior to preserve.

## Behavior and states

Entry points, actions, success, empty/loading/error/conflict states, cancellation,
recovery and where the user returns.

## Permissions and personal/shared behavior

Who can see and change each part? What happens after archive or access removal?

## API, MCP and connections

Inventory persisted mutations and authorized reads. Name the shared domain
operation, API route and MCP tool for each, whether an MCP App UI is needed, and
affected connection types/scopes/consent/revocation/privacy. Include cross-surface
adapter verification. Describe mappings in prose or a table in the PR template.

## Design reference

Reviewed preview and source commit, phone/desktop screenshots, existing components
and intentional proposals for new components/tokens. Label mocks and confirm
backend isolation before test writes.

## Acceptance criteria

Observable outcomes, including keyboard/focus, phone layout and failure recovery.

## Open questions and evidence

Assumptions, mocks, checks performed and checks still required.

## Module ownership

Name the owning product module (or shared platform), contribution points and public
routes/tools to preserve. Follow [Product modules](/docs/modules); include client/server
boundaries and independent app, dashboard, MCP and notification preferences.
